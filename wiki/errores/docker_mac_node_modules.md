# Guía: Resolución de Problemas de Dependencias Cruzadas en Docker (macOS vs Linux)

Esta guía documenta el problema técnico común de **Conflictos de Arquitectura en Node Modules** cuando se desarrolla desde un entorno host macOS (o Windows) hacia contenedores Docker que operan sobre Linux (índice común en las distribuciones basadas en Alpine o Debian usadas en proyectos Node).

## 🐛 El Problema: "Módulo no encontrado" o "Falla de binarios"

### ¿Qué sucede exactamente?
Cuando ejecutas `npm install` localmente en tu terminal de **Mac**, npm o Node descargan y compilan librerías binarias nativas (como `@swc/core` usado por NestJS, ó `esbuild` usado por Vite) en la arquitectura propia de tu máquina, es decir, `darwin-x64` o `darwin-arm64` (si es un Mac M1/M2/M3).

Sin embargo, tu archivo `docker-compose.yml` usa la instrucción `volumes:` para enlazar (montar) tu disco duro local con el interior del contenedor. 
* El contenedor es **Linux** (`linux-x64` o `linux-arm64`).
* El contenedor ve e intenta usar los archivos generados en `/node_modules` por tu Mac.
* Los binarios dentro del `/node_modules` del Mac **no funcionan** en el Linux de Docker.

### Mensajes de error comunes vinculados
* `Failed to load "@swc/cli" and/or "@swc/core"` (NestJS)
* `The package "@esbuild/linux-x64" could not be found` (Vite / React)
* Errores mencionando `bindings`, `glibc`, `musl`, o `node-gyp`.
* Un paquete está, pero de repente otro (como `@sentry/react` recientemente instado en otra rama) tira error al importar a pesar de estar en el `package.json`.

---

## 🛡️ Cómo evitar este problema (Mejores Prácticas)

Hay dos maneras principales de aislar los `node_modules` del Mac de los `node_modules` del contenedor.

### 1. Usar volúmenes anónimos para aislar `node_modules` (Solución actual en tu Docker)
En tu `docker-compose.dev.yml` hemos puesto:
```yaml
    volumes:
      - ./frontend/smart-economat-frontend:/app # Monta todo tu codigo...
      - /app/node_modules                       # ...PERO excluye y aísla node_modules
```
Esta técnica (llamada *Volumen Anónimo* en el `node_modules`) significa que Docker guardará su propio directorio `node_modules` compilado en Linux y **no lo sobreescribirá ni sincronizará** con el `node_modules` de tu Mac. 

**⚠️ Inconveniente**: Si instalas una dependencia desde tu terminal de Mac (ej. `npm install axios`), tu Mac re-escribe el `package.json`, pero el volumen anónimo de Docker **no se entera automáticamente** de que necesita descargar el código de `axios`. Tienes que decirle explícitamente al contenedor que refresque ese volumen.

### 2. Ejecutar comandos Node SOLO dentro del contenedor
Para evitar la desincronización, la mejor práctica de desarrollo con Docker es nunca correr comandos `npm` en el ordenador anfitrión (Mac), sino dispararlos directamente sobre el contenedor:
```bash
# En lugar de ejecutar npm install en tu terminal de Mac, hazlo en la terminal de Docker
docker exec -it smarteconomat-dev-frontend-1 npm install la-nueva-libreria
```

---

## 🛠️ Cómo solucionarlo (Paso a Paso)

Si cambias de rama, de PC, o un compañero sube cambios que alteraron el `package.json` y los contenedores de repente se rompen (o detectas el error de SWC o esbuild):

### Opción A (La "Elegante") - Instalar desde dentro del contenedor
Esta es la forma rápida si el contenedor llegó a levantarse y no se detuvo por error grave:
1. Accede e instala para el frontend: `docker exec -it smarteconomat-dev-frontend-1 npm install`
2. Instala para el backend: `docker exec -it smarteconomat-dev-backend-1 npm install`
3. Reinicias el contenedor: `docker restart smarteconomat-dev-frontend-1`

### Opción B (El "Nuclear Clean") - Forzar reconstrucción de volúmenes
Si el `Volumen Anónimo` se ha quebrado por completo, o el contenedor se detiene y no permite arrancar (status `Exit 1`), debes aniquilar el contenedor y su volumen anónimo, obligando a Docker a crear un volumen en Linux desde 0.

```bash
# Para el Frontend:
docker compose -f docker-compose.dev.yml rm -sfv frontend
docker compose -f docker-compose.dev.yml up -d --build frontend

# Para el Backend:
docker compose -f docker-compose.dev.yml rm -sfv backend
docker compose -f docker-compose.dev.yml up -d --build backend
```
*(El modificador `-v` o `--volumes` dentro de `rm` es el encargado y causante de borrar el volumen anónimo conflictivo).*

---

### Resumen Rápido (TL;DR)
1. Los binarios de NodeJS que instala MacOS (`node_modules`) son incompatibles con Linux en Docker.
2. Si un paquete falla diciendo que falta la versión para Linux u otro componente central, tus `node_modules` están desincronizados.
3. Lo arreglas con `docker compose rm -sfv <servicio>` y reconstruyéndolo con `docker compose up -d --build <servicio>`.
