# Resolución de dependencias cruzadas en Docker entre host y contenedor

Esta guía documenta el fallo típico en el que el host instala dependencias nativas para su propia plataforma, pero los contenedores Docker necesitan binarios compilados para Linux.

## Síntoma

Los servicios dejan de arrancar o fallan al importar paquetes nativos aunque estén declarados en `package.json`.

Mensajes habituales:

- `Failed to load "@swc/cli" and/or "@swc/core"`
- `The package "@esbuild/linux-x64" could not be found`
- errores sobre `bindings`, `glibc`, `musl` o `node-gyp`

## Causa

Cuando se ejecuta `npm install` en macOS o Windows, npm descarga binarios nativos para esa plataforma. Si después el proyecto monta ese `node_modules` dentro de un contenedor Linux mediante `volumes`, el contenedor intenta reutilizar binarios incompatibles.

El problema es especialmente visible en dependencias como `@swc/core`, `esbuild` o librerías con extensiones nativas.

## Prevención recomendada

### 1. Aislar `node_modules` dentro del contenedor

En desarrollo con Docker, el servicio debe montar el código fuente pero mantener un volumen propio para `node_modules`:

```yaml
volumes:
  - ./frontend/smart-economat-frontend:/app
  - /app/node_modules
```

Eso evita que el `node_modules` del host sobreescriba el del contenedor.

### 2. Instalar dependencias dentro del contenedor

En lugar de ejecutar `npm install` en el host, conviene hacerlo en el servicio Docker correspondiente:

```bash
docker exec -it smarteconomat-dev-frontend-1 npm install
docker exec -it smarteconomat-dev-backend-1 npm install
```

## Recuperación

### Opción A: reinstalar dentro del contenedor

Si el servicio llega a arrancar, reinstala dependencias dentro del propio contenedor y reinícialo.

```bash
docker exec -it smarteconomat-dev-frontend-1 npm install
docker exec -it smarteconomat-dev-backend-1 npm install
docker restart smarteconomat-dev-frontend-1
docker restart smarteconomat-dev-backend-1
```

### Opción B: recrear contenedor y volumen

Si el servicio ya no arranca, elimina el contenedor junto con su volumen anónimo y vuelve a construirlo:

```bash
docker compose -f docker-compose.dev.yml rm -sfv frontend
docker compose -f docker-compose.dev.yml up -d --build frontend

docker compose -f docker-compose.dev.yml rm -sfv backend
docker compose -f docker-compose.dev.yml up -d --build backend
```

El flag `-v` fuerza la recreación del volumen anónimo y evita reutilizar binarios corruptos o incompatibles.

## Resumen operativo

- No reutilizar `node_modules` del host dentro de contenedores Linux.
- Si cambian dependencias, reinstalarlas dentro del contenedor.
- Si hay desincronización grave, recrear servicio y volumen con `rm -sfv` y `up --build`.
