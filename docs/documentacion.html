Indice

Introduccion

SmartEconomat es una aplicacion web para la gestion integral del economato escolar. El sistema cubre catalogo, compras, recepciones, inventario, produccion, seguridad y exportacion documental desde una arquitectura cliente-servidor basada en React, NestJS, PostgreSQL, Redis y Docker.

Objetivo

El objetivo principal del sistema es automatizar el control del inventario escolar, reducir errores humanos, mejorar la trazabilidad del stock y facilitar la gestion de pedidos, recepciones y elaboraciones culinarias. El objetivo de esta memoria es describir ese sistema con la precision necesaria para defensa academica, mantenimiento tecnico y continuidad del proyecto.

Alcance

La memoria cubre el sistema principal SmartEconomat: frontend web, backend NestJS, base de datos PostgreSQL, cache Redis, despliegue Docker y estrategia de testing. Se excluye del cuerpo principal ElectronInstaller, que aparece en el repositorio como una capa administrativa complementaria todavia no integrada al mismo nivel funcional que el sistema core.

Definiciones clave

Termino Definicion tecnica
FIFO Metodo operativo que prioriza el uso del lote mas antiguo disponible para evitar caducidades y sobrecostes.
LIFO Metodo alternativo mencionado en requisitos, aunque el sistema enfatiza FIFO para control de inventario perecedero.
PMP Precio medio ponderado calculado a partir del historico de compra y de la relacion producto-proveedor.
PedidoUsuario Agregado de negocio que representa la necesidad del usuario o del centro antes de su separacion por proveedor.
PurchaseBatch Lote administrativo que agrupa varios pedidos internos para tratarlos como una unidad operativa de compra.
Envelope API Estructura estandar de respuesta basada en success, message, data y meta.

Descripcion general

SmartEconomat funciona como una plataforma de gestion de economato para centros educativos. El sistema combina operaciones de compra y almacen con un modulo docente para profesores y alumnos, ademas de un modelo de seguridad basado en JWT, roles y permisos granulares.

Stack principal

React 19, Vite 6, NestJS 11, TypeORM 0.3, PostgreSQL, Redis 7 y Docker Compose.

Tipo de arquitectura

Cliente-servidor con API REST versionada en /api/v1 y servicios de apoyo para cache, ficheros y exportacion.

Dominio de negocio

Catalogo, proveedores, pedidos, recepciones, incidencias, inventario, recetas, produccion y gestion educativa.

Vision del sistema

El sistema digitaliza el ciclo completo del economato. La informacion fluye desde la interfaz web hacia servicios frontend centralizados, continua por la API REST del backend y se persiste en PostgreSQL con apoyo de Redis para cache de permisos y ciertos comportamientos operativos. El resultado es una plataforma modular que integra gestion de stock, trazabilidad de movimientos, resolucion de incidencias y generacion de documentos PDF o XLSX.

Restricciones

  • La memoria y el propio sistema no cubren facturacion, nomina ni gestion contable.
  • El proxy de produccion publica la SPA y la API, pero no expone Swagger al exterior salvo configuracion adicional.
  • El backend rechaza payloads fuera de contrato mediante validacion estricta.
  • Las rutas heredadas en singular, como /proveedor o /inventario, se mantienen por compatibilidad contractual.

Arquitectura

La solucion adopta una arquitectura cliente-servidor con API REST centralizada. El frontend delega todo el transporte HTTP en servicios propios, mientras que el backend concentra validacion, reglas de negocio, seguridad y persistencia a traves de modulos por dominio.

Componentes principales

El frontend funciona como capa de presentacion y orquestacion de usuario. La logica de negocio se encapsula en servicios NestJS distribuidos por modulo. TypeORM y PostgreSQL gestionan el almacenamiento transaccional, mientras Redis optimiza cache y estados de apoyo. La exposicion publica se realiza mediante Nginx en produccion, con proxy hacia la API interna.

Los componentes transversales mas relevantes son I18nValidationPipe, GlobalExceptionFilter, TransformInterceptor, JwtAuthGuard, RolesGuard, PermisosGuard y el sistema de throttling.

Modulos backend visibles

auth, usuario, roles, permisos, plantillas-roles, admin, dashboard, producto, proveedor, inventario, movimiento, merma, ubicacion, openfoodfacts, pedido, pedido-draft, recepcion, recepcion-draft, incidencia, albaran, distribucion, receta, preparacion, profesor, alumno, archivo y export.

Flujo de datos

  1. El usuario opera desde la SPA, que centraliza las llamadas HTTP en servicios frontend.
  2. La API recibe la peticion bajo el prefijo /api/v1 y aplica guards, pipes y filtros globales.
  3. El controlador delega la logica a un servicio de dominio que puede abrir transacciones con DataSource o QueryRunner.
  4. TypeORM persiste o consulta la informacion en PostgreSQL y, cuando aplica, Redis participa como cache de permisos.
  5. La respuesta sale envuelta por el interceptor en el formato comun de API, salvo streams binarios como PDF, XLSX o archivos.

Frontend

El cliente web se construye con React 19, Vite 6, Material UI 7 y React Router 7. La aplicacion funciona como SPA, centralizando toda la comunicacion HTTP en una capa de servicios que opera sobre fetch nativo con cookies httpOnly. El estado global se gestiona con Context API (sesion, tema, notificaciones) y Redux Toolkit (permisos efectivos).

Patrones de diseno

Diseno atomico y co-locacion

Los componentes se organizan en tres niveles: componentes UI puros en components/ui/, componentes de negocio en components/common/ y paginas completas en pages/. Los tipos, helpers y estilos se co-localizan junto al archivo que los consume (.types.ts, .helpers.ts).

Composicion sobre prop drilling

Se prioriza el patron children y Context API para evitar el paso excesivo de propiedades. La sesion, el tema y las notificaciones se proveen globalmente; los permisos efectivos se almacenan en un slice Redux para actualizacion reactiva.

Gestion de estado
  • AuthContext: sesion, usuario, login/logout, refresco periodico.
  • ThemeContext: modo claro/oscuro.
  • ToastContext: notificaciones globales.
  • Redux (permissionsSlice): permisos efectivos del usuario.
  • localStorage: solo preferencias UI (metricas dashboard, hint de sesion).

Capa de servicios HTTP

La comunicacion con el backend se centraliza en services/api.service.ts, que encapsula fetch nativo con credentials: 'include' para enviar la cookie httpOnly en cada peticion. Existe un listener global de 401 que emite un evento AUTH_UNAUTHORIZED para disparar el cierre de sesion automatico.

Cada modulo de negocio expone un servicio especifico (~32 servicios) con sus tipos asociados en archivos .types.ts. Los servicios encapsulan endpoints, payloads y transformaciones de datos, impidiendo que los componentes dependan directamente de la forma de la API.

Enrutado y proteccion de rutas

El enrutado se gestiona con React Router v7 desde AppRouter.tsx. Cada ruta protegida se envuelve en un componente ProtectedRoute que espera a que isAuthResolved sea verdadero antes de evaluar permisos. Las rutas publicas (/login, /reset-password) usan PublicRoute para redirigir usuarios autenticados.

<ProtectedRoute
  requiredPermission="productos:listar"
  requiredAnyPermissions={["usuarios:listar", "profesor:gestionar_slots"]}
>
  <Administracion />
</ProtectedRoute>

Base de datos

El almacenamiento principal se apoya en PostgreSQL 16 con 41 entidades TypeORM distribuidas en 8 dominios funcionales. Casi todas las tablas heredan una BaseEntity comun con UUID v7, marcas temporales, soft delete y control de version, lo que proporciona trazabilidad, orden temporal y seguridad ante concurrencia.

ER - Catalogo y stock

Nucleo del catalogo maestro: productos, proveedores, relacion de abastecimiento, stock por ubicacion, historial de precios, movimientos de inventario y mermas. La tabla pivote producto_proveedor es el centro de todas las operaciones de stock y compras.

ER - Compras

Flujo de compras en tres niveles: el usuario crea un pedido_usuario con lineas, que se descompone en pedidos individuales por proveedor. Los pedidos pueden agruparse en un purchase_batch para tramitacion conjunta.

ER - Recepcion e incidencias

Registro de entrada fisica de mercancia con trazabilidad documental. La tabla recepcion_pedido enlaza recepciones con pedidos; recepcion_producto detalla cada linea recibida. Las incidencias se detectan por diferencias de cantidad o estado y se resuelven trazablemente. Los albaranes enlazan recepciones con documentos de proveedor.

ER - Produccion y recetas

Modela la transformacion de materias primas en productos elaborados. Una receta define ingredientes con cantidades y mermas; la preparacion planifica la ejecucion; el lote de produccion registra costes reales y porciones disponibles para consumo posterior.

ER - Seguridad y usuarios

Sistema RBAC dinamico con tres niveles: plantillas de rol predefinidas, roles asignables a usuarios, y permisos granulares por modulo y accion. Cada usuario puede tener permisos adicionales o excluidos independientes de sus roles. Los archivos se vinculan al usuario que los sube.

ER - Educativo y distribucion

Extension educativa: profesores con CIAL vinculados 1:1 a usuarios, slots de clase por aula y numero, y alumnos asignados a profesor y slot. La distribucion prepara y entrega pedidos de usuario a ubicaciones destino, opcionalmente vinculados a un slot de clase.

ER - Borradores temporales

Persistencia del lado servidor para formularios complejos en curso. Ambos borradores almacenan el payload completo en JSONB con versionado y TTL opcional, permitiendo recuperar formularios incompletos entre sesiones.

Relaciones entre dominios

Los diagramas anteriores muestran las relaciones internas de cada dominio. Las conexiones mas importantes entre dominios son:

  • Producto → ProductoProveedor → PedidoProducto: el catalogo alimenta directamente las lineas de pedido.
  • PedidoProducto → RecepcionProducto: cada linea de pedido se verifica en la recepcion.
  • RecepcionProducto ↔ Incidencia: relacion 1:1 opcional para discrepancias detectadas.
  • Recepcion → Movimiento → Inventario: la recepcion completada genera movimientos que actualizan stock.
  • RecetaIngrediente → Producto: los ingredientes referencian productos del catalogo maestro.
  • Usuario → Profesor (1:1) y Usuario → Alumno (1:1): extension educativa del modelo de usuario.
  • PedidoUsuario → Distribucion: los pedidos de usuario se distribuyen a ubicaciones destino.
  • AlumnoSlot → Ubicacion: los slots de clase pueden tener una ubicacion de entrega asociada.

API

La API REST del backend expone 238 endpoints distribuidos en 37 controladores, todos bajo el prefijo /api/v1. El proyecto utiliza @nestjs/swagger para generar documentacion OpenAPI interactiva en tiempo real, accesible en la ruta /api/v1/docs del servidor. Esta seccion resume la estructura, convenciones y rutas mas representativas; para el detalle exhaustivo de cada endpoint (parametros, DTOs, schemas de respuesta y codigos de error) se recomienda consultar directamente la interfaz Swagger del proyecto en ejecucion.

Documentacion interactiva con Swagger

Al levantar el backend en desarrollo (npm run start:dev), la documentacion OpenAPI completa se genera automaticamente en http://localhost:3000/api/v1/docs. Alli se puede explorar cada endpoint, ver los DTOs de entrada/salida, probar peticiones en vivo y descargar la especificacion en formato JSON. En produccion, Swagger no se expone por defecto por seguridad.

Autenticacion y autorizacion

El sistema implementa autenticacion JWT con cookies httpOnly y autorizacion en dos niveles:

  • JwtAuthGuard: valida el token JWT en cada peticion protegida. Los endpoints publicos se marcan con @Public().
  • PermisosGuard + @RequirePermissions: verifica que el usuario tenga los permisos granulares necesarios (ej: productos.crear, inventario.ajustar_stock). Los permisos se resuelven combinando roles, plantillas, permisos adicionales y excluidos.
  • AdminGuard: restriccion adicional para endpoints exclusivos de administracion del sistema (roles, permisos, plantillas).

SmartEconomat implementa un modelo de seguridad por capas: autenticacion JWT en cookie httpOnly, control de acceso RBAC con 88 permisos granulares sobre 19 modulos, proteccion CSRF mediante Double Submit Cookie y limitacion de peticiones inteligente. Pipeline de guards

Cada peticion HTTP pasa por una cadena de guards registrados globalmente como APP_GUARD. Un decorador @Public() permite eximir endpoints concretos (login, registro, forgot-password).

  1. JwtAuthGuard — Valida el JWT y extrae el usuario. Si la ruta es publica, se omite.
  2. RolesGuard — Si el controlador declara @Roles(...), verifica que el usuario pertenezca a la familia de roles requerida.
  3. PermisosGuard — Combina permisos declarados a nivel de controlador y metodo con @RequirePermissions (AND) o @RequireAnyPermission (OR). Los roles elevados (ADMIN, SUPER_ADMIN) pasan automaticamente.
  4. SmartAuthThrottlerGuard — Aplica limites de tasa por identidad del usuario.

Proteccion CSRF

Se implementa el patron Double Submit Cookie (sin estado en servidor). Al iniciar sesion, el backend genera un token aleatorio fuerte y lo envia como cookie XSRF-TOKEN (httpOnly: false). En cada peticion mutante (POST, PUT, DELETE, PATCH), el frontend lee la cookie y la reenvia en la cabecera X-XSRF-TOKEN. El middleware CsrfMiddleware valida que ambos valores coincidan.

Propiedad de la cookie Valor Motivo
httpOnlyfalseEl frontend necesita leer el valor para incluirlo en la cabecera.
sameSitestrictMaxima proteccion contra envio automatico entre origenes.
securetrue (produccion)Solo se transmite por HTTPS.

Limitacion de tasa (throttling)

El SmartAuthThrottlerGuard aplica tres niveles de limite de forma inteligente: prioriza la identidad del usuario autenticado o el email/username de login sobre la IP, evitando penalizar a usuarios legitimos detras de NAT compartido.

Nivel Ventana Limite Aplicacion
auth60 s500 peticionesEndpoints de autenticacion.
write60 s1 000 peticionesPOST, PUT, DELETE.
read60 s5 000 peticionesGET y consultas.

Cache de permisos

Los permisos efectivos de cada usuario se almacenan en Redis con clave user:permissions:{userId} y TTL de 300 segundos. Esto reduce el coste de autorizacion repetitiva: la primera peticion calcula los permisos (formula descrita arriba) y las siguientes los leen directamente de cache. La invalidacion se puede realizar por usuario, en lote o globalmente.

Arquitectura de pruebas

  1. Cada worker inicializa una instancia propia de pg-mem y una app NestJS reutilizable.
  2. Los seeders se ejecutan una sola vez por worker y se encapsulan en un seed snapshot.
  3. Cada archivo de pruebas puede capturar un segundo snapshot para restauracion por test.
  4. bcrypt se reduce a un coste minimo en test mediante mock para eliminar latencia artificial.

Conclusiones

SmartEconomat presenta una base tecnica coherente para un TFG DAW: arquitectura modular en backend y frontend, contratos API explicitados, persistencia relacional robusta, seguridad multicapa basada en roles y 88 permisos granulares, y una infraestructura de despliegue reproducible con Docker Compose. La documentacion del repositorio es amplia y permite reconstruir con precision tanto la intencion funcional como la implementacion real.

Evaluacion

Desde el punto de vista academico, el proyecto destaca por la trazabilidad entre requisitos, modulos y persistencia; por la separacion clara entre presentacion (React 19 + MUI 7), logica de negocio (NestJS modular) y almacenamiento (PostgreSQL + TypeORM); por un modelo de seguridad completo (JWT cookie-first, RBAC dinamico, CSRF y throttling inteligente); y por una estrategia de testing poco habitual en proyectos de este nivel, basada en pg-mem y snapshots.

Desde el punto de vista operativo, el sistema resuelve el flujo central de economato: catalogo, pedidos de usuario, compras consolidadas, recepcion con incidencias, inventario FIFO, mermas, produccion desde recetas y exportacion documental en PDF y XLSX.

Los puntos donde el repositorio muestra margen de mejora estan mas ligados a formalizacion que a carencias estructurales: faltan evidencias cuantitativas publicadas para algunos RNF, Swagger no queda expuesto en produccion por defecto y ciertos objetivos del documento de requisitos original, como la aplicacion de impuestos en detalle de albaran, no aparecen explicitados en los contratos visibles.

Mejoras futuras

  • Publicar una matriz formal de permisos por rol y por modulo, util para auditoria y soporte.
  • Instrumentar metricas de rendimiento reales en produccion para respaldar los RNF con datos.
  • Ampliar la evidencia de pruebas en frontend y accesibilidad, especialmente en dispositivos tablet.
  • Decidir si Swagger debe exponerse de forma controlada en produccion o mantenerse solo para entornos internos.
  • Integrar o descartar definitivamente ElectronInstaller como componente de entrega del producto.
