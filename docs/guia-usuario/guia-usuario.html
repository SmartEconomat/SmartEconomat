1. Introducción

1.1 Objetivo del sistema

SmartEconomat es una aplicación web de gestión integral diseñada específicamente para el economato de una escuela de hostelería y cocina. Su misión es digitalizar y centralizar el ciclo completo de aprovisionamiento: desde la solicitud de materias primas hasta su consumo en el aula, pasando por la recepción de mercancía, el control de inventario, la trazabilidad de movimientos y la gestión de mermas e incidencias.

El sistema sustituye los procesos manuales —hojas de cálculo, albaranes en papel, comunicaciones informales— por flujos digitales auditables, con control de acceso por rol, exportación de datos y registro exhaustivo de toda actividad.

1.2 Público objetivo

  • Personal administrativo y de almacén (Administrador / Superadministrador): gestiona el catálogo completo, aprueba pedidos, recepciona mercancía y supervisa el inventario.
  • Profesorado (Profesor): solicita materiales para sus clases, registra preparaciones, reporta mermas e incidencias.
  • Alumnado (Alumno): consulta el catálogo de productos, recetas y preparaciones relacionadas con su módulo.

1.3 Tecnologías principales

Frontend

  • React 18 + TypeScript
  • Material UI v5 (MUI)
  • Vite (bundler)
  • React Router v6
  • react-i18next (ES/EN)
  • Redux Toolkit (estado global)

Backend

  • NestJS + TypeScript
  • TypeORM + PostgreSQL
  • JWT (autenticación)
  • UUID v7 (generados en DB)
  • Swagger / OpenAPI
  • Docker + Docker Compose
ℹ️ Internacionalización
La interfaz está completamente traducida a español e inglés. El usuario puede cambiar el idioma desde su perfil o desde el menú de ajustes (icono de configuración en la barra lateral).

2. Visión general de la aplicación

2.1 Problema que resuelve

Las escuelas de hostelería gestionan grandes volúmenes de ingredientes perecederos con fechas de caducidad críticas, multitud de proveedores y docenas de clases simultáneas. SmartEconomat resuelve:

  • Falta de trazabilidad en el consumo de materiales por aula y por receta.
  • Pérdida de albaranes y facturas en papel.
  • Ineficiencia en la gestión de pedidos multi-proveedor.
  • Ausencia de control FEFO (First Expired, First Out) en el inventario.
  • Dificultad para detectar y gestionar mermas e incidencias con proveedores.

2.3 Arquitectura general

La aplicación sigue una arquitectura cliente-servidor desacoplada:

  • Frontend SPA (React) expuesto en puerto 5173 (dev) / 443 (prod).
  • API REST (NestJS) expuesta en :3000, con documentación Swagger en /docs.
  • Base de datos PostgreSQL en :5432, con migraciones TypeORM.
  • Todo orquestado con Docker Compose (entornos dev y prod separados).

La navegación está basada en un router dinámico: el menú lateral se construye automáticamente a partir de los permisos del usuario autenticado; si no dispone del permiso listar de un módulo, la ruta no aparece en el menú ni es accesible directamente.

4. Módulo de Autenticación

Las rutas públicas del sistema son /login, /reset-password y /reset-password/:token. Cualquier usuario no autenticado que intente acceder a una ruta protegida es redirigido automáticamente a /login.

4.1 Pantalla de inicio de sesión

Figura 4.1 — Pantalla de inicio de sesión (Login.png)

La pantalla de login presenta un diseño de dos paneles: un panel izquierdo con imagen decorativa y el formulario de autenticación a la derecha (o en columna única en móvil). Los elementos identificados son:

  1. Campo de nombre de usuario o email — acepta tanto el nombre de usuario como la dirección de correo electrónico registrada.
  2. Campo de contraseña — con botón para mostrar/ocultar el texto.
  3. Botón "Iniciar Sesión" — envía las credenciales al endpoint POST /auth/login y recibe un token JWT en la respuesta. Dicho token se almacena en el contexto de autenticación de la aplicación.
  4. Enlace "¿Olvidaste tu contraseña?" — navega a la pantalla de recuperación.
  5. Enlace "Crear cuenta de alumno" — permite el autorregistro de nuevos alumnos.
ℹ️ Rate Limiting
Los endpoints de autenticación tienen aplicado un limitador estricto (máx. 5 intentos por 15 minutos) para prevenir ataques de fuerza bruta, implementado con @nestjs/throttler y almacenamiento en Redis.

4.2 Registro de alumno

Figura 4.2 — Formulario de autorregistro de alumno

El formulario de registro de alumno solicita:

  • Nombre completo (requerido)
  • Email — debe ser único en el sistema
  • Nombre de usuario — único, sin espacios
  • Contraseña y confirmación — mínimo 8 caracteres, al menos una mayúscula, un número y un carácter especial
  • Selección de profesor — el alumno elige el profesor al que queda vinculado

Tras el registro, la cuenta queda pendiente de activación por parte del administrador. El alumno no podrá iniciar sesión hasta que un ADMIN o SUPER_ADMIN active su cuenta.

4.3 Creación de profesor

Figura 4.3 — Pantalla de creación de cuenta de profesor

A diferencia del alumno, la creación de cuentas de profesor se realiza generalmente desde el módulo de Administración por un ADMIN. Sin embargo, existe un flujo específico accesible desde la pantalla de login para que un potencial profesor solicite acceso. Los datos solicitados son similares al registro de alumno, pero el rol asignado es PROFESOR. La cuenta requiere igualmente activación administrativa.

4.4 Recuperación de contraseña

Figura 4.4 — Pantalla de recuperación de contraseña

El flujo de recuperación de contraseña sigue estos pasos:

  1. El usuario introduce su dirección de email en el formulario de recuperación (POST /auth/forgot-password).
  2. El sistema genera un token seguro de un solo uso y lo envía por email al usuario.
  3. El usuario hace clic en el enlace del email, que le lleva a /reset-password/:token.
  4. El usuario introduce y confirma su nueva contraseña.
  5. El sistema valida el token (comprueba expiración y uso único) y actualiza la contraseña hasheada con bcrypt.

8. Módulo Recetas

El catálogo de recetas (escandallos) define las preparaciones que se ejecutan en el aula. Cada receta lista los ingredientes, sus cantidades brutas y netas (con porcentaje de merma aplicada), así como el rendimiento y el coste estimado.

ℹ️ Cálculo de merma en ingredientes
El campo mermaAplicada de cada ingrediente acepta valores entre 0 y 99,99 %. Al introducirlo, el sistema calcula automáticamente la cantidad bruta a pedir: cantidadBruta = cantidadNeta / (1 − merma/100). Este valor es el que se utiliza al ejecutar la producción para descontar del inventario.

8.2 Ejecución de receta — Cocinar

Con el permiso recetas:cocinar, el usuario puede ejecutar la producción de una receta. Este proceso:

  1. Verifica que haya stock suficiente para todos los ingredientes (con criterio FEFO: First Expired First Out, prioriza los lotes de caducidad más próxima).
  2. Descuenta las cantidades brutas de cada ingrediente del inventario generando movimientos de tipo PRODUCCION_CONSUMO.
  3. Crea un nuevo lote en el inventario del producto resultado con movimiento PRODUCCION_RESULTADO.
  4. Registra un ProduccionLote con el usuario, la fecha y el rendimiento obtenido.

Si el stock es insuficiente para algún ingrediente, la ejecución se cancela con error antes de realizar ningún descuento.

El módulo de pedidos gestiona el ciclo completo de aprovisionamiento desde la solicitud hasta la recepción en almacén. Soporta tres tipos de entidades: Pedido de compra (purchase_batch), Pedido de usuario (pedido_usuario) y el Pedido clásico (pedido).

10. Módulo Recepción

El módulo de recepción gestiona la entrada física de mercancía al almacén. Opera mediante un asistente de pasos (wizard) de cuatro etapas que guía al operario durante el proceso de conteo y validación de la mercancía recibida.

10.1 Paso 1 — Selección de pedidos

Figura 10.1 — Paso 1: Selección del pedido a recepcionar

El operario selecciona el lote de compra o pedido pendiente que va a recepcionar. El sistema filtra automáticamente los pedidos en estado POR_RECEPCIONAR.

10.2 Paso 2 — Escaneo / Conteo

Figura 10.2 — Paso 2: Escaneo y conteo de productos recibidos

En este paso el operario va registrando, línea por línea, la cantidad real recibida de cada producto. Dispone de:

  • Escáner de código de barras — mediante la Web Serial API (lector USB) o cámara del dispositivo
  • Báscula — integración con balanza electrónica vía puerto serie para peso automático
  • Búsqueda manual — autocompletado por nombre si no hay código de barras
  • Crear nuevo producto — modal para dar de alta un producto no existente en catálogo durante la recepción

10.3 Paso 3 — Revisión

Figura 10.3 — Paso 3: Revisión de diferencias y asignación de lotes

La revisión muestra una comparativa entre la cantidad pedida y la cantidad contada. Si hay diferencias, el sistema las clasifica automáticamente como:

  • FALTANTE — se recibió menos de lo pedido → se genera incidencia automática
  • EXCESO — se recibió más de lo pedido
  • DEFECTUOSO — unidades recibidas en mal estado

También se asigna en este paso la fecha de caducidad y la ubicación de almacenamiento para cada lote recibido.

10.4 Paso 4 — Finalización

Figura 10.4 — Paso 4: Confirmación y resultado de la recepción

Al confirmar la recepción el sistema:

  1. Crea los registros de inventario (lotes) con movimientos tipo ENTRADA_COMPRA.
  2. Actualiza el estado del pedido/lote a RECEPCIONADO o PARCIAL si hay diferencias.
  3. Genera automáticamente las incidencias correspondientes a las diferencias detectadas.
  4. Vincula el albarán del proveedor si ya fue digitalizado.
⚠️ Borrador de recepción
Al igual que los pedidos, el wizard de recepción guarda automáticamente el progreso como borrador. Si el operario cierra el navegador accidentalmente, puede retomar desde donde lo dejó. Si detecta un borrador anterior de otro usuario, muestra un diálogo de conflicto.

12. Módulo Distribución

El módulo de distribución gestiona el traslado de materiales recepcionados desde el almacén central hacia las aulas o destinos de los profesores. Es el puente entre la recepción de mercancía y el consumo en preparaciones.

12.2 Entrega de distribución

Figura 12.2 — Registro de entrega de una distribución

12.3 Historial de distribuciones

Figura 12.3 — Historial de distribuciones realizadas

El flujo de distribución funciona así:

  1. El sistema detecta los pedidos de usuario en estado APROBADO o CONSOLIDADO con stock disponible y los muestra en la pestaña "Disponibles".
  2. El administrador selecciona las líneas de producto a distribuir e indica la cantidad, la ubicación origen y la ubicación destino (puede ser el slot de aula del alumno).
  3. Al crear la distribución, su estado inicial es EN PREPARACIÓN.
  4. Al confirmar la entrega, el estado cambia a ENTREGADO y se generan los movimientos de inventario correspondientes (DISTRIBUCION).
  5. La distribución puede cancelarse con un motivo antes de ser entregada.

El sistema sugiere automáticamente la ubicación destino basándose en el slot de aula asignado al alumno que realizó el pedido.

El inventario controla el stock físico por lote y por ubicación. Implementa el criterio FEFO (First Expired, First Out): los lotes con fecha de caducidad más próxima se consumen primero. El sistema registra la trazabilidad completa de cada movimiento.

15. Módulo Mermas

Las mermas son las pérdidas de producto registradas en el sistema. Pueden originarse en diferentes contextos: durante la recepción, en la producción, por caducidad, rotura o inventario.

Figura 15.1 — Módulo de mermas visto por el Profesor

Figura 15.2 — Modal de reporte de merma desde una preparación

Los motivos de merma disponibles son:

  • Rotura — el producto se ha roto o derramado
  • Deterioro — degradación por temperatura, humedad u otros
  • Hurto — desaparición por sustracción
  • Error de preparación — desperdicio durante el cocinado
  • Otros — causa no clasificada

La página de mermas muestra estadísticas agregadas (por motivo y por producto) junto al historial de registros individuales. El profesor puede reportar mermas directamente desde el listado de preparaciones.

16. Módulo Incidencias

Las incidencias registran las discrepancias detectadas durante la recepción de mercancía. Se crean automáticamente cuando hay diferencias entre la cantidad pedida y la recibida, pero también pueden crearse manualmente.

Figura 16.1 — Módulo de incidencias visto por el Profesor

El ciclo de vida de una incidencia:

NUEVA → EN_AJUSTE → PENDIENTE_VALIDACIÓN → RESUELTA

También puede terminar en CANCELADA o INVÁLIDA.

Cada línea de incidencia tiene su propio estado de reclamación:

  • PENDIENTE — sin acción por parte del proveedor
  • RECLAMADO — se ha presentado reclamación formal
  • ABONADO — el proveedor ha emitido abono/factura de crédito
  • REENVIADO — el proveedor ha vuelto a enviar la mercancía

Para resolver una incidencia, el usuario (con permiso incidencias:resolver) puede ajustar las cantidades recibidas línea a línea, cambiar los estados de reclamación e indicar el estado final (resuelta, cancelada o inválida).

Las preparaciones son las ejecuciones de recetas registradas en el sistema. Cada vez que un profesor o administrador "cocina" una receta, se crea un registro de preparación (ProduccionLote) con todos los datos de la ejecución.

21. Flujos de usuario completos

21.1 Flujo de aprovisionamiento completo

  1. Profesor crea un pedido — selecciona productos del catálogo, indica cantidades y lo envía. Estado: PENDIENTE.
  2. Admin aprueba el pedido — revisa el pedido del profesor y lo aprueba. Estado: APROBADO.
  3. Admin consolida pedidos semanales — agrupa pedidos de la misma semana en un lote de compra y lo envía al proveedor.
  4. Proveedor entrega la mercancía — el operario inicia el wizard de recepción, escanea los productos y registra las cantidades reales.
  5. Recepción finalizada — el sistema crea los lotes de inventario con sus fechas de caducidad y ubicaciones.
  6. Digitalización del albarán — el operario sube el PDF del albarán del proveedor y lo vincula a la recepción.
  7. Distribución al aula — el administrador prepara y confirma la entrega al slot de aula del profesor.
  8. Profesor ejecuta la receta — descontando los ingredientes del inventario y creando el lote de producto final.

21.2 Flujo de gestión de incidencia

  1. Durante la recepción se detecta una diferencia → el sistema crea automáticamente la incidencia en estado NUEVA.
  2. El administrador revisa la incidencia y actualiza el estado de reclamación de cada línea (RECLAMADO).
  3. El proveedor responde → el administrador actualiza a ABONADO o REENVIADO.
  4. Se marca la incidencia como RESUELTA con las observaciones de resolución.

21.3 Flujo de alta de nuevo alumno

  1. El alumno accede a /login y hace clic en "Crear cuenta de alumno".
  2. Completa el formulario de registro y selecciona su profesor.
  3. El sistema crea la cuenta con estado inactivo y notifica al administrador.
  4. El administrador accede a Administración → Usuarios, localiza al nuevo alumno y activa su cuenta.
  5. El alumno ya puede iniciar sesión con sus credenciales.

24. Conclusiones

SmartEconomat representa una solución digital completa y robusta para la gestión del economato de una escuela de hostelería. Sus principales fortalezas son:

  • Trazabilidad completa: cada movimiento de stock queda registrado con usuario, fecha y motivo.
  • Control FEFO: el sistema prioriza el consumo de los lotes más próximos a caducar, reduciendo el desperdicio alimentario.
  • Sistema de permisos granular: cada usuario ve y puede hacer exactamente lo que su rol permite, sin necesidad de código adicional.
  • Flujos guiados: el wizard de recepción y los borradores automáticos de pedidos previenen pérdidas de datos y guían al usuario paso a paso.
  • Internacionalización completa: la interfaz está disponible en español e inglés con soporte para añadir más idiomas.
  • Arquitectura escalable: el backend NestJS con módulos desacoplados y el frontend React con lazy loading permiten crecer en funcionalidad sin degradar el rendimiento.

Recomendaciones de uso

  • Realizar el conteo de inventario físico mensual y contrastar con el inventario digital para detectar desviaciones.
  • Activar las notificaciones de stock bajo mínimo para anticipar la rotura de stock.
  • Formar al profesorado en el uso del módulo de pedidos para que las solicitudes lleguen consolidadas y bien documentadas.
  • Mantener actualizado el catálogo de productos y sus precios de proveedor para que los costes de escandallo sean precisos.
  • Revisar periódicamente las mermas por producto para detectar patrones de desperdicio y tomar medidas correctoras.
